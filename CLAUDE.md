## Design system
- UI follows `design/` (POS Design System v0.2: one theme, graphite chrome + paper panes; window chrome in `chrome.rs` = workspace tabs, per-page toolbar, status bar; panes with header strips via `w::pane_uis`). Read `design/docs/07-egui-handoff.md` before UI work, and the matching `design/docs/components/<Name>.md` before building or changing a widget. `design/reference/` is a visual reference only — do not port its HTML/CSS/JS.
- Colours/sizes come only from `apps/pos-desktop/src/ui/` (`Theme::of(ui)`: `p` palette, `m` metrics; `space`, `radius`, `type_scale`). Never hard-code `Color32` or pixel sizes in screens. `ui/tokens.rs` is copied from `design/rust/tokens.rs` and skipped by rustfmt — regenerate it from the design system rather than hand-editing.
- Money: i64 satang; display through `ui::format` (grouped, 2 decimals, U+2212 minus) in the IBM Plex Mono family, right-aligned, never truncated.
- One saffron primary button per view (money-moving commit). Key actions keep a text label and a keyboard shortcut; icon-only actions need an accessible name and tooltip.
- Never put wrapped text in a justified layout (`ui.columns`, `Popup::menu`, `top_down_justified`): egui justifies by stretching glyph gaps, which detaches Thai vowels and tone marks. Use `w::columns` and set `Layout::top_down(Align::Min)` on menu popups that hold paragraphs. Product/bill/category names go through `ui::text::wrapped` for Thai-safe breaks.
- There is no light/dark mode. The device look is an accent preset (`accent.txt`: saffron, jade, ocean, plum, ink) and a shape (`shape.txt`: soft = floating panes, square = edge-to-edge, 3 px corners); route corner radii through `Theme::radius` / `pane_radius` and pane gaps through `pane_gap`. Text drawn on the graphite chrome/canvas uses `t.chrome()` / `t.chrome_muted()`.
- Check UI changes in Soft + Square, ไทย + English, Compact + Touch, at 1000×700 and 1280×820 (and at least one non-saffron accent).

## Architecture in brief

- `apps/pos-desktop` (egui/eframe UI) → `crates/pos-service` (serializable `Request`/`Reply` business protocol, `Query`/`Data`, `handle()` — the one dispatcher, shared with future paired devices) → `crates/pos-core` (Diesel/SQLite persistence and transactions) → `crates/pos-domain` (Money, Cart, Sale, Shift, PaymentMethod, validation). Domain never imports UI or storage; no repository traits and no async runtime in the shop apps/crates (the separate cloud server `apps/pos-cloud` uses tokio/axum); network services are opt-in (multi-device plan: docs/multi-device.md). New business commands go into `pos_service::Request`/`Reply`/`handle` and are mapped in `worker::request`/`worker::event`; device-local work stays in the worker.
- A single worker thread (`apps/pos-desktop/src/worker.rs`) owns the one SQLite connection. UI screens send typed requests over a bounded channel and render the worker's `Data` results; no DB work in paint. Worker requests a repaint on completion.
- Migrations are plain SQL in `crates/pos-core/migrations/NNN_*.sql`, applied by `database.rs` via `PRAGMA user_version` inside an IMMEDIATE transaction; unknown future versions refuse startup; before migrating an existing older database `Pos::open` keeps it as `<db>.pre-v<old>.sqlite3` (once per version). `schema.rs` is hand-maintained to mirror the SQL — update both when adding a migration (current is 026; next is 027). Old-schema test fixtures drop migration 026 first with `tests/support::DROP_OUTBOX`.
- Writes (checkout, void, shift open/close, cash movement) are single IMMEDIATE transactions that revalidate catalog/shift state and commit receipt, stock, held-cart removal, ledger entry and shift totals together. Retry identity (cart ID / UUID) is looked up before the active-shift gate.
- Registers (schema 24, multi-device phase 0c, `pos-core/src/shifts.rs`): `registers(id, name, created_at, retired_at)` seeded with `MAIN_REGISTER` (`Uuid::from_u128(1)`); `shifts.register_id` (default main, no FK so old-schema fixtures can drop it); one open shift **per register** (`one_open_shift_per_register`). `Pos` carries the connection's register (`register()`, `use_register`, default main on open); `active_shift`, `open_shift` and the checkout/refund/void/cash-movement shift gate use it, so a payment against another register's shift is refused. Sales, refunds and movements know their register through their shift. `Shift.register_id` deserializes old snapshots as main. `add_register(id, name)` is retry-safe and needs Settings. Stock and catalog are shop-wide.
- Devices (schema 25, `pos-core/src/devices.rs`) and the hub (`crates/pos-hub`): paired devices (`devices`: kind register/kitchen/ordering, register, SHA-256 token hash, paired/revoked/last seen); `pair_device` (after the hub's one-time code; a register device gets its own register with the device's ID), `revoke_device` (Settings), `device_login`; both audited as `ActivityKind::Device`. `pos-hub`: TLS with a self-signed hub identity pinned by fingerprint, 6-digit pairing codes (5 min, single use, 5 tries), length-prefixed JSON frames, one thread per device, `Executor` runs device jobs on the database owner via `Pos::as_device` (per-device session/register), change notices from `pos_service::Versions`. Desktop: Settings → Shop devices (`hub_ui.rs`, `hub.json` off by default) starts the hub; the worker runs device jobs between its own commands and notifies devices of local writes (`Command::SetHub`, `Event::DevicesChanged`). Preset `settings-devices-pairing` (loopback, pairing code on screen). Client mode: `device.json` beside the data makes the app a paired device (`Worker::start_remote`, commands go to the hub; device-local commands refused; `Event::Connection`). The main register mirrors `shop.json` + logo into `app_settings` `shop_profile` (`Pos::publish_profile`, device-local `Command::PublishShop`, not a protocol request); paired registers apply `Data.shop_profile` (`App::apply_shared_shop`, shop/templates read-only via `App::shop_managed`). Reports: `DailySummary.registers` (ledger row → shift → register; refunds where given). iPad ordering web app (`pos-hub/src/web.rs`, `webtls.rs`, static `crates/pos-hub/web/`): HTTPS on hub port + 1 with a leaf signed by the shop CA (`web-ca.der` / `web-ca-key.der`, device files), setup page + `.mobileconfig` on HTTP port + 2 (QR in Settings → Shop devices); `/api/pair`, `/api/state`, `/api/call`, `/api/changes` long poll; ordering only, never payment.
- Cloud outbox (schema 26, multi-device phase 2, `pos-core/src/outbox.rs`): SQLite triggers queue a pointer row `outbox(seq, kind, record_id)` in the same transaction as every write the cloud keeps (sales, voids, refunds, ledger, stock/ingredient movements, invoices, credit notes, purchasing, Activity; mutable records such as products, categories, option sets, promotions, ingredients, tables, staff, suppliers, orders, shifts and registers keep one pending row, deletes queue a tombstone). `outbox_batch` reads each record's current JSON (`KINDS`, never the staff PIN hash), `outbox_ack` deletes stored rows, `requeue_all` (migration and relink) queues everything. The server keys records by (kind, id), never seq, so restores and resends are safe. New tables the cloud should see need a trigger + a `KINDS` entry. Sync on the main register: desktop `cloud.rs` (`cloud.json` device file, `Syncer` thread, worker cloud jobs) and `cloud_ui.rs` (Settings → Devices & cloud); owner edits apply via `Pos::apply_cloud_change` as the Cloud member (core `cloud.rs`, `Session::cloud`, never reachable from a protocol request). Encrypted daily cloud backups: `cloud_backup.rs` (`.phcloud`, Argon2id key from the owner's backup password kept in `cloud.json`, ChaCha20-Poly1305 via ring); restore accepts a `.phcloud` path in Settings → Data & backup.
- Staff/permissions (schema 9, `pos-core/src/staff.rs`): `authorize` runs inside each write transaction after the retry lookup and shift gate. No active staff = unattributed, unchanged behaviour. Roles are data (schema 12 `roles` table; owner fixed in code): each permission is Allow / Approval / Deny per role. Approval gives `ApprovalRequired`, which the desktop replays as `Command::Approved` with another member's PIN (one-shot, no self-approval); Deny gives `Forbidden`, never overridable. Staff snapshots on records are never rewritten. Sessions are in memory; a PIN is not database protection.
- VAT (schema 10, `pos-core/src/tax.rs`): `Sale.tax` is snapshotted only at checkout; full tax invoices have their own number, one per sale, and are refused for voided/refunded sales. Credit notes (schema 16, `credit_notes`): every void or partial refund of a sale with a full tax invoice issues one in the same transaction (`tax::credit_note`), own CN number, `source_id` = the void/refund ID, values before VAT (per invoice / correct / difference) plus the difference's VAT.
- Receipts, voids and closed shifts are immutable JSON snapshots; legacy JSON must deserialize via defaults without being rewritten.
- `shop.json` (shop profile, PromptPay ID, print `templates`), `receipt-logo.png`, `printer.json`, `hub.json`, `hub-cert.der`, `hub-key.der`, `web-ca.der`, `web-ca-key.der`, `device.json`, `cloud.json`, `product-images.txt` (Sell tile pictures on/off), `auto-backup.json`, `auto-lock.json`, `accent.txt`, `shape.txt`, `density.txt`, `language.txt`, `window.txt`, `current-bill.txt` and `drawer-count-<shift>.json` live beside the DB, are owned by the desktop app, and are excluded from DB backups (`VACUUM INTO`). Recovery folders carry the business sidecars (`shop.json`, `current-bill.txt`, drawer drafts, `receipt-logo.png`) but not printer/display/automatic-backup/idle-lock device files.
- The open bill autosaves through the held-cart store (background worker commands that never set `busy`); `current-bill.txt` marks it for restore. Checkout's existing held-row delete keeps paid bills consistent.
- Product options (schema 006, `options_json`) are priced only inside checkout via `pos_domain::price_with_options`; the desktop cart total and noncash review use the same function.
- Promotions (schema 17, `promotions` table JSON + `uses` counter; `pos_domain::apply_promotions`, `pos-core/src/promotion.rs`, desktop `promo_ui.rs`): percent / baht-per-unit off a product or category, buy X get Y (within one line), spend-over bill discounts; optional days, hours (Bangkok, may wrap midnight), dates, coupon code (`Cart.coupons`, unique, case-insensitive) and max uses. Checkout reloads promotions inside its transaction at payment time; the desktop prices through the same function (`App::promoted`). A cashier's own line/bill discount always wins; each line takes its single best promotion. Promotion discounts become ordinary line/bill discounts, are snapshotted as `SaleLine.promotion` and `Sale.promotions` (`PromoUse`), count once per bill toward `uses`, and do not count toward the cashier's discount limit or the Discount activity event.
- Ingredients and recipes (schema 18, `ingredients` JSON + `stock_milli` column, `ingredient_movements`, `products.recipe_json`; `pos_domain::ingredient`, `pos-core/src/ingredient.rs`, desktop `ingredients_ui.rs` and the recipe section in `catalog_ui.rs`): quantities are integer thousandths of the ingredient's unit. Checkout deducts `ingredient_use` of the catalog recipes read in its transaction (one `sale` movement per ingredient, `sale_id` set); stock may go negative and never refuses a sale. A void returns exactly the sale movements (`void`); partial refunds return nothing. Edits never change stock; receive / remove (reason) / count are retry-safe movements (Stock permission). Recipes may only add active, existing ingredients. Option recipes (schema 19, `products.option_recipe_json`, `OptionRecipe { choice_id, ingredient_id, amount }`, signed): `line_recipe` applies the chosen choices to the base recipe per unit and drops ingredients at or below zero; checkout deducts that. Reports: `DailySummary.promotions` (`PromoSales`: bills and amount per promotion on the sale day, whole voids subtract, partial refunds do not) and `DailySummary.ingredients` (`IngredientUsage`: sale use net of voids, manual removals, cost at today's unit cost) from `ingredient::usage`.
- Shared option sets (schema 22, `option_sets` JSON + position, `products.option_sets_json`; `pos-core/src/option_set.rs`, desktop `option_sets_ui.rs`): each set is one `OptionGroup` with stable IDs. Every product load (`find_product`, `products`, `find_by_code`, `save_product`'s result) appends the product's sets after its own groups (`option_set::resolve`), so pricing, checkout, the options sheet and option recipes are unchanged; `Product::own_options()` / `ProductInput.option_sets` keep them apart and `save_product` stores only own groups, refuses unknown sets (`OptionSetNotFound`) and validates own + set groups and the option recipe together. `link_option_set` (bulk), `delete_option_set` (unlinks everywhere) and unlinking drop option recipe rows of the set's choices. The `products` table has more than 16 columns, so diesel's `32-column-tables` feature is on.
- Categories (schema 21, `categories(name, position)`, `pos-core/src/category.rs`, desktop `categories_ui.rs`): products keep the category name; saving/importing a product with a new name adds it at the end (`category::ensure`). `catalog_counts` lists categories in position order, empty ones included, uncategorised last (this order drives Sell and Products). `rename_category` updates every product in one transaction and merges into an existing name; `reorder_categories` needs exactly the current names; `delete_category` moves products into another category or uncategorised. All need Catalog and are recorded as Product activity.
- Product pictures (schema 20): small PNGs (≤ 256 px, ≤ 512 KB) in `product_images`, apart from product rows; `products.image_rev` (`Product.image`) changes on every set/remove (`Pos::set_product_image`, Catalog permission; `save_product` keeps it). The desktop imports PNG/JPEG (path or drop) in `images.rs`, loads pictures in the background only for visible tiles and the open editor, and keeps at most 120 textures (least recently used dropped). Pictures are in the database, so backups and recovery carry them.
- Discounts (line/bill, baht/percent) live only in cart/receipt JSON (no migration) and are priced only by `pos_domain::price_sale` (checkout transaction, desktop cart, noncash review) in the fixed order line discounts → bill discount → service charge → VAT on top (++ prices) → cash rounding (cash only); `price_bill` is the discounts-only wrapper. Pricing settings are JSON in `app_settings` key `pricing` (schema 11). Partial refunds use `refund_share(line.net(), …)`; `SaleLine.total` stays gross. PromptPay ID is an optional `shop.json` field; its QR is still a manually confirmed Transfer.
- Split payment (no migration): `Pos::checkout_split` takes `SplitPayment { tenders, cash_given }`; `normalized()` merges parts per method (cash, transfer, card), drops zeros, needs ≥2 methods and cash given ≥ the cash part. Split bills are never cash-rounded and the parts must equal the exact total. The `sales` row keeps the first noncash part as `payment_method` with zero cash/change columns; the receipt JSON (`Sale.tenders`, serde default empty; `paid_by()`) is authoritative. One ledger row per part (`shifts::record_all`, sale counted once), only the cash part moves drawer expected; reports record each part by method. A split void refunds each part to its own method (`SaleVoid.tenders`, `refunded_by()`); partial refunds pick one of the sale's methods, capped at what it paid (`InvalidRefundMethod` / `RefundExceedsMethod`).
- Split bill: `Pos::split_bill` (one IMMEDIATE transaction, `pos_domain::split_cart` on the stored `sent` state) moves units and their kitchen-sent units to a new held bill without a table or guests, so nothing fires or cancels; a percent bill discount stays on both, a baht one on the original only; retry by the new bill ID returns the stored pair.
