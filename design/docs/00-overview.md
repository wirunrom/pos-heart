# POS Design System

ภาษาการออกแบบสำหรับผลิตภัณฑ์หน้าร้าน (ขาย ครัว หลังร้าน ลูกค้า) เริ่มจากแอปขายหน้าร้าน desktop ที่ทำงานแบบ offline
**v0.1 · Proposed** — ส่วนใหญ่พร้อมนำไปทำ แต่ยังไม่ได้ทดสอบกับผู้ใช้จริงหรือใน egui จริง (ดู *สถานะ* ด้านล่าง)

> "POS Heart" เป็นแค่ชื่อชั่วคราว ชื่อผลิตภัณฑ์ โลโก้ และสีแบรนด์อยู่ใน `brand.*` ชั้นเดียว
> tokens และ components ทั้งหมดตั้งชื่อตาม*หน้าที่* เปลี่ยนแบรนด์ได้โดยไม่ต้องแตะ component — ดู 02 Tokens

## ทิศทาง: "Calm counter"

ระบบนี้เอาข้อดีของทั้งสามแนวทางที่สำรวจไว้มารวมกัน:

| มาจาก | สิ่งที่เก็บไว้ |
|---|---|
| **Studio** (ฐานหลัก) | พื้นผิวเป็นชั้น · โครงสีกลาง + สี signal สีเดียว · ตัวสลับ workspace + `Ctrl K` · สลับ density ได้ · บิลพักเป็นแท็บ · สถานะ offline/กะอยู่ในแถบบนตลอด |
| **Ledger** | เงินใช้ตัวเลขความกว้างเท่ากัน (IBM Plex Mono) · ชิดขวาทุกที่ · คำใบ้ F-key บนเดสก์ท็อป · เส้นแบ่งบางแทนกรอบหนา |
| **Counter** | โหมดสัมผัสที่ใหญ่จริง (48–64px) · ปุ่มเงินด่วน · stepper ในตะกร้า · ตัวเลขยอดชำระใหญ่ อ่านได้จากระยะ 1 เมตร |

**เอกลักษณ์ที่มองเห็น:** พื้นกระดาษอุ่น (warm stone) + หมึกเข้ม + **ทองหญ้าฝรั่น (saffron) สีเดียว**ใช้กับ "การกระทำที่ทำให้เงินเคลื่อน" เท่านั้น — รับเงิน, ยืนยัน, บันทึก
ผลลัพธ์คือหน้าจอที่สงบ อ่านง่าย และ*รู้ทันทีว่าปุ่มไหนคือขั้นต่อไป*

## หลักการออกแบบ (เรียงตามลำดับเมื่อขัดกัน)

1. **เงินต้องถูกและอ่านครบ** — แสดงทุกหลักรวมทศนิยม ห้ามย่อ ห้ามตัด ใช้ตัวเลขความกว้างเท่ากันและชิดขวา ยอดขาย / รายรับ / เงินในลิ้นชัก / สถานะชำระ เป็นคนละคำและคนละ component
2. **ขั้นต่อไปชัดเจนเสมอ** — มีปุ่ม accent (saffron) ได้แค่หนึ่งปุ่มต่อหนึ่งมุมมอง การกระทำสำคัญมีข้อความกำกับ ไม่พึ่ง icon หรือสีอย่างเดียว
3. **เร็วสำหรับคนประจำ เข้าใจได้สำหรับคนใหม่** — ทุก action มีทั้งปุ่มที่มองเห็นและคีย์ลัด ฟีเจอร์ขั้นสูงซ่อนไว้ด้วย progressive disclosure ไม่ใช่ซ่อนตลอด
4. **ความผิดพลาดต้องแก้ได้** — ใช้ undo ก่อน confirm ถามยืนยันเฉพาะสิ่งที่ย้อนกลับไม่ได้ และบอกผลที่จะเกิดเป็นตัวเลข
5. **Offline คือสภาพปกติ** — ไม่มีหน้าจอไหนหยุดทำงานเพราะไม่มีเน็ต สถานะ sync มองเห็นได้ แต่ไม่ขัดจังหวะการขาย
6. **สอดคล้องกัน ไม่ใช่เหมือนกันทุกหน้า** — ใช้ tokens และ components ร่วมกัน แต่ layout เลือกตามงานของแต่ละหน้า (ขาย ≠ ปิดกะ ≠ ครัว)

## ใช้ระบบนี้อย่างไร

| ต้องการ | ไปที่ |
|---|---|
| สี ตัวอักษร ระยะ รูปทรง motion และ accessibility | **01 Foundations** |
| ค่า tokens, การตั้งชื่อ, Light/Dark, density | **02 Tokens** · `tokens.json` · `tokens/tokens.dtcg.json` |
| เลือก component / ดูสถานะของแต่ละตัว | **03 Components** + การ์ด component แต่ละตัว |
| พฤติกรรมที่ใช้ซ้ำ (ค้นหา, draft, undo, งานเงิน, sync) | **04 Patterns** |
| โครงเมนู และที่วางฟีเจอร์ในอนาคต | **05 Information architecture** |
| เพิ่ม/เปลี่ยน component, versioning, checklist QA | **06 Governance** |
| นำไปทำใน Rust/egui | **07 egui handoff** |
| ดูการใช้งานจริง | การ์ดกลุ่ม **Reference screens** (ขาย · สินค้า · ปิดกะ · โต๊ะ · รายงาน · ข้ามอุปกรณ์) |

ตัวอย่าง HTML/CSS ในการ์ดทุกใบเป็น **design reference** (`components/bundle.css` = รูปแบบ class ที่ใช้เป็นสเปก) ไม่ใช่โค้ดแอปจริง
ทุกหน้าจอที่ติดป้าย *ข้อมูลตัวอย่าง / Sample data* ใช้ข้อมูลสมมติ

## สถานะ: อะไรใช้ได้ อะไรยังทดลอง

| ระดับ | ความหมาย | ตัวอย่าง |
|---|---|---|
| **Ready** | สเปกครบ นำไปทำได้เลย ทดสอบ contrast แล้ว | Button, TextField/MoneyField, ProductTile, CartLine, OrderSummary, StatusBadge, Feedback, Overlay, StateView, Navigation, DataTable |
| **Experimental** | ใช้ได้ แต่ต้องพิสูจน์กับผู้ใช้หรือใน egui ก่อนจะ lock | สลับ density, ปุ่มเงินด่วน, command bar `Ctrl K`, StatTile/Chart, ฟอนต์ Thai ใน egui |
| **Future exploration** | ไว้ stress-test ระบบเท่านั้น ยังไม่ใช่ roadmap | โต๊ะ/โซน, kitchen display, จ่ายผสม, ส่วนลด, หลายสาขา, tablet |

สิ่งที่**ต้องพิสูจน์ต่อ**: (1) Thai shaping ของ IBM Plex Sans Thai ใน egui · (2) อัตราการกดผิดในโหมดสัมผัสบนจอ 15″ · (3) พนักงานใหม่หา "พักบิล / ยกเลิกบิล" ได้เองไหม · (4) dark theme ในร้านที่แสงจ้า
