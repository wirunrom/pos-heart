# Multi-device and cloud plan

**สรุป (ตัดสินใจแล้ว 2026-10-16):** ใช้แบบ **เครื่องหลักในร้าน + เครื่องลูกในวง LAN + ซิงก์ขึ้นคลาวด์** การขายไม่พึ่งอินเทอร์เน็ต: เครื่องหลัก (hub) ของแต่ละร้านเป็นผู้เขียนข้อมูลคนเดียว เครื่องขายที่สอง จอครัว และแท็บเล็ตรับออเดอร์ส่งคำสั่งผ่าน LAN ให้ hub ทำ กฎเงิน สต็อก เลขใบเสร็จ/ใบกำกับภาษี และ transaction เดิมจึงใช้ได้ทั้งหมด เมื่อมีเน็ต hub ส่งข้อมูลที่แก้ไม่ได้ (ใบเสร็จ คืนเงิน กะ การเคลื่อนไหวสต็อก) ขึ้นคลาวด์ และรับสินค้า/ราคา/โปรที่เจ้าของแก้จากที่อื่นลงมา เน็ตหลุดก็ขายต่อได้ แค่คิวรอส่ง ไม่ทำแบบทุกเครื่องมีข้อมูลเองแล้วซิงก์กันเต็มรูปแบบ เพราะต้องแก้ข้อมูลชนกันเรื่องเงินและสต็อก

ลำดับ: **เฟส 0** เตรียมภายใน (ไม่มีเครือข่าย ผู้ใช้ไม่เห็นความต่าง) → **เฟส 1** เครื่องลูกใน LAN → **เฟส 2** คลาวด์ (สำรองนอกร้าน + รายงานบนเว็บ + แก้สินค้าจากส่วนกลาง) → **เฟส 3** หลายสาขา

Status: decided direction; phase 0 in progress — **Phase 0 done (2026-10-16)**: request/result types are serializable, `crates/pos-service` is the single dispatcher the desktop worker uses, and schema 24 adds registers with one shift per register (sales/refunds/movements are attributed through their shift rather than new columns), and `pos_service::{Topic, Versions, changes}` give in-memory change notices (0d: per-topic versions in the hub process, no table — a reconnecting device refreshes everything). Tablet decision: **iPad first** (see §6). Nothing listens on the network yet; the app is still single-register and offline.

## 1. Constraints that shape the design

- **One writer per shop.** A single worker thread owns the only SQLite connection (`apps/pos-desktop/src/worker.rs`); every write is one IMMEDIATE transaction. SQLite over a network share is unsafe, so devices never open the hub's file.
- **Invariants that assume one writer** and therefore stay on the hub: receipt, tax-invoice, credit-note and kitchen-ticket sequences; stock checked and deducted inside checkout; one open bill per table; retry identity (cart ID / request UUID) looked up before the shift gate; immutable receipts, voids, refunds, closed shifts and tickets.
- **Selling must not depend on the internet.** The LAN keeps working when the uplink drops; the cloud is never in the payment path.
- **Nothing listens by default.** Network services are explicit opt-in device settings with their own security (AGENTS.md "no network" rule, extended deliberately).
- **No async runtime** (AGENTS.md). Services use plain threads and blocking I/O, like the worker and the printer queue.

## 2. Target architecture

```
          ┌──────────── shop LAN ────────────┐                 ┌──── cloud (phase 2+) ────┐
 tablet ──┤                                  │                 │                          │
 register2┤──TLS──▶ hub service ─▶ pos-service ─▶ SQLite (hub)  │  ingest  ◀── outbox ─────┤ hub uploader
 kitchen ─┤          (threads)      (dispatch)                   │  catalog ──▶ inbox ──────┤ hub downloader
          └──────────────────────────────────┘                 │  web dashboard / backup  │
                                                               └──────────────────────────┘
```

- **`pos-service` crate (new):** the serializable `Request` / `Response` protocol and one dispatcher `handle(&mut Pos, &Session, Request) -> Result<Response>`. The desktop worker calls it in-process; the hub service calls it for remote devices. One code path, one set of tests.
- **Hub service:** opt-in on one machine. Accepts paired devices over TLS, runs each request on the worker (same queue, same single connection), returns the response, and pushes change notices.
- **Clients:** the same desktop binary in *client mode* (second register, kitchen screen on another PC) uses a network transport instead of the local worker. Tablets: see §6 (platform decision).
- **Cloud (phase 2):** a separate server project. The hub writes an outbox in the same transactions as the business writes, uploads it idempotently, and applies downstream catalog documents through ordinary `pos-service` requests attributed to "HQ".

## 3. Phase 0 — groundwork (no network, no visible change)

Each step lands with tests and keeps the app working exactly as today.

**0a. Serializable protocol.** Add `Serialize`/`Deserialize` to every request and result type (`ProductInput`, `PaymentRequest`, `SplitPayment`, `VoidRequest`, `RefundRequest`, `ShiftCount`, `StockRequest`, `StaffInput`, query types, …). Round-trip tests for each. Stored JSON formats must not change (serde attributes keep the existing field names/defaults).

**0b. `pos-service` crate.** Move the business half of `worker::run` (sales, shifts, catalog, stock, staff, settings, tables/kitchen, purchasing, reports, activity) behind `Request`/`Response`; device-local work stays in the desktop worker (backups and recovery, file import/export paths, product-picture files, auto-backup policy, demo seeding). `Command::Approved` becomes a request wrapper carrying the approver. A protocol version constant. Tests drive the service directly.

**0c. Registers.** Migration 024: `registers (id, name, created_at, retired_at)` seeded with one "main" register; `register_id` on shifts, sales, voids/refunds and cash movements (existing rows → main). "One active shift" becomes one active shift **per register**; drawer expected, close and statements per register; daily reports keep shop totals and add a per-register breakdown. Each device stores its register in a device file (`device.json`: device ID, register ID). With one register nothing changes for the user.

**0d. Change notices.** A monotonically increasing `data_version` per topic (catalog, held bills/tables, kitchen, shift, settings) bumped inside write transactions, so clients (and the local UI) can refresh only what changed. Locally this replaces some full refreshes.

## 4. Phase 1 — devices on the shop LAN

Progress (2026-10-16): **1a done** — `crates/pos-hub`: length-prefixed JSON frames (`wire`: Hello/Call ↔ Welcome/Refused/Answer/Changed, `WireError` kind + message, 16 MiB limit), `Hub` (accept thread, one thread per device, a newer connection of a device replaces the older, change notices to every device after each successful write, `Hub::notify` for writes made on the counter itself), `Executor` (runs jobs on the database owner as the device via `pos_core::DeviceContext` / `Pos::as_device`, so sign-in, approvals, PIN lockout and register are per device) and a blocking `Client`. **1b done** — TLS (rustls with the ring provider) on every connection: the hub has a self-signed identity (`tls::Identity`, `hub-cert.der` / `hub-key.der` beside the database, device files), devices pin its SHA-256 fingerprint learned at pairing (`tls::short` = first 4 bytes for comparing screens). Pairing: `Hub::open_pairing` shows a 6-digit code valid 5 minutes, used once, cancelled after 5 wrong tries; the device sends code + ID + name + kind and receives a random token (only its SHA-256 is stored). Schema 25 `devices` (name, kind register/kitchen/ordering, register, token hash, paired/revoked/last seen); a register device gets its own register (ID = device ID), others use the main register; pairing and revocation (Settings) are Activity events (`ActivityKind::Device`). Token checks, pairing and requests all run as jobs on the database owner. Each connection is one thread with read timeouts (`wire::Framer`) so it both reads requests and sends change notices. **1c (hub side) done** — Settings → Shop devices (`hub_ui.rs`, `hub.json`, off by default, Settings permission): turning it on starts the hub on port 47810 (all interfaces; macOS/Windows may ask to allow incoming connections), shows the LAN address, the check code (`tls::short`), connected count, "Pair a device" with the 6-digit code and countdown, and the paired devices with Revoke. The worker runs device jobs between the counter's own commands (`Worker::hub_submit`, `pos_hub::Executor`), tells devices about the counter's own writes (`Command::SetHub(Notifier)`), refreshes the counter after device writes (`Event::DevicesChanged`) and on revoke forgets the session and drops the connection. `hub.json`, `hub-cert.der` and `hub-key.der` stay with this computer on recovery. Desktop test `hub_tests.rs` pairs a device with the real worker, writes from both sides and revokes. **1c (device side) done** — client mode: a computer with `device.json` (hub address, device ID, token, pinned fingerprint, name, kind, register) starts `Worker::start_remote` instead of opening a local database. Commands become `Request`s sent with `pos_hub::Client` (one retry with the same call ID after reconnecting), replies become the usual events, business errors come back as the same `pos_core::Error` (`WireError` carries kind + permission/text/number/domain payloads; anything else is `Error::Remote`), change notices trigger a background refresh, and device-local commands (backups, recovery, files, demo) are refused. The status bar shows "Main register connected / not connected"; Settings → Shop devices on an unpaired computer offers "Use this computer as a shop device" (address, 6-digit code, name, register or kitchen; pairing runs in the background and writes `device.json`; restart to switch) and, on a device, its main register, status and "Stop being a shop device". A device skips the shop-setup screen. Desktop test pairs a client-mode worker with a hub-mode worker. Printer settings stay per computer by design. Closed after 1e: the shop profile is shared — the main register mirrors its `shop.json` and receipt logo into `app_settings` (`shop_profile`, `pos_core::SharedProfile`, device-local `Command::PublishShop` at start and after every shop/template/logo change, `Notifier::touch(Topic::Settings)`); `Data.shop_profile` carries it and a paired register applies it (keeping its own start-in-Sell), caches `shop.json`/logo locally and shows shop details and document layout read-only. Reports break sales and refunds down by register (`DailySummary.registers`, via each record's ledger row → shift → register; refunds count where given; a Reports "Registers" tab when there is more than one register and CSV rows). **1d done** — mDNS (`pos_hub::discovery`, `mdns-sd`, threads only): the running hub announces `_posheart._tcp` with the shop name, port and certificate fingerprint; "Find main registers" on an unpaired computer lists them to fill the address; a device that cannot connect looks every third attempt for a hub with its pinned fingerprint and follows a new address (saved to `device.json`). The announcement is only a hint: pinning still decides trust. `tests/discovery.rs` is `#[ignore]` (needs multicast; passes on a Mac on the LAN; `dns-sd -B _posheart._tcp` shows the service). **1e done** — the iPad ordering web app, served by the hub (`pos_hub::web`, `webtls`, static files in `crates/pos-hub/web/`); details below as built. The desktop starts it with the hub: HTTPS on hub port + 1 (47811), setup page on HTTP port + 2 (47812); Settings → Shop devices shows the setup URL as a QR plus the app URL, and pairing uses the same "Pair a device" code. Beyond the design: `GET /api/state` returns a lean snapshot for the app (menu = active on-sale products with their resolved options, categories in order, active tables, held bills, staff names and sign-in state, change total) from one ordinary `Refresh`; `/api/call` takes `{id, request}` and answers `{ok: Reply}` or `{error: WireError}` (business refusals are HTTP 200; 401 = pair again). The app signs staff in per iPad (PIN pad), replays `ApprovalRequired` as `Approved` with a manager's PIN, edits notes and guests, retries a dropped request once with the same call ID, and never pays. CSP `default-src 'self'`, no inline script/style. `web-ca*.der` are device files (excluded from backups). Test `crates/pos-hub/tests/web.rs` (HTTPS client trusting the CA): setup page/profile on HTTP, pairing refused then accepted, 401s, state, SendKitchen of a table bill, long-poll wake-up, TableBusy refusal, revoke. Checked in a browser at 1024×700 through a CA-trusting local proxy; **not yet tried on a real iPad** (profile install, Home Screen, touch). The leaf is issued for the LAN address at hub start: a changed address needs the hub restarted. Design as planned:
  - **Web certificate:** a separate shop CA (`web-ca.der` / `web-ca-key.der`, rcgen `IsCa::Ca`) signs a leaf for the current LAN IPs + `posheart.local` (EKU serverAuth, ≤ 825 days), regenerated at hub start. iPad Safari trusts it after installing `/ca.mobileconfig` (`com.apple.security.root` payload) and enabling full trust. The desktop protocol keeps its pinned self-signed identity unchanged.
  - **Hub web endpoints:** plain HTTP `/setup` (instructions + profile download; desktop shows its URL as a QR). HTTPS: static app (`index.html`/`app.js`/`app.css` embedded with `include_str!`), `POST /api/pair {code, name}` → ordering device + token, `POST /api/call` (Bearer `device.token`, body `Request` JSON → `Reply` JSON, same job queue and `Executor`), `GET /api/changes?since=` long poll on `Versions`. A cache of verified web tokens is cleared on revoke. Minimal HTTP/1.1 over rustls `StreamOwned`, Content-Length bodies ≤ 1 MiB, threads only.
  - **Ordering UI (vanilla JS, design tokens, Touch density):** tables → menu (categories, products, options sheet) → bill → Send to kitchen / Hold; no payment by default. Uses Refresh, Resume, Hold, SendKitchen; the kitchen diff against stored `sent` prevents duplicate tickets.
  - **Concurrent edits (done after 1e):** a held bill saved by another device since a copy was loaded refuses that copy (`BillChanged`; revision + editor in the cart JSON, `dining::claim`), including send to kitchen, split and payment; the counter reloads (or adopts a newer save when it has no unsaved edits) and the iPad app reloads. Tests: `crates/pos-core/tests/dining.rs`, `crates/pos-hub/tests/web.rs`, desktop `hub_tests.rs`. Hub tests (`crates/pos-hub/tests/hub.rs`, loopback): two registers selling shared stock, a payment resent after a dropped connection returns the same receipt, cross-register shift refused, per-register drawers, change notices, refusals for unknown devices/tokens, per-device sign-in.


- **Hub setting:** Settings → Devices → "Allow other devices" (off by default; requires the Settings permission). Shows hub name, address and paired devices.
- **Pairing:** the hub shows a 6-digit code valid for 5 minutes. The device sends the code and its public key; the hub issues a per-device token and the device pins the hub's certificate fingerprint. Pairing and revocation are Activity events. Wrong codes are rate-limited.
- **Transport:** TLS (rustls, blocking) on a LAN-bound port; length-prefixed JSON frames carrying `{version, device, request_id, request}`. `request_id` doubles as retry identity, so a resent payment after a dropped connection returns the stored result, as today.
- **Discovery:** mDNS service advertisement; manual IP as fallback.
- **Staff:** each connection has its own signed-in session; PIN sign-in, approvals and permissions run on the hub exactly as now. The device ID is recorded in Activity.
- **Change push:** the hub streams `data_version` changes; clients refresh the affected data (kitchen screens and the table floor update live across devices).
- **Offline behaviour:** a client that loses the hub shows "ไม่ได้เชื่อมต่อเครื่องหลัก" and blocks writes; the bill being edited stays in memory and is held on the hub when the connection returns. Payments are never queued on a client.
- **Device roles:** second register (own register and drawer), kitchen display, ordering device (no payment permission by default).
- **Tests:** in-process client↔hub over loopback; dropped-connection retries for checkout, refund and close shift; two registers with separate drawers selling the last unit of stock; table bill opened from two devices (second refused); revoke during a session.

## 5. Phase 2 — cloud, phase 3 — branches

**Phase 2 progress (2026-10-16):** decided to build the server in this repository (Rust, axum + PostgreSQL, run locally with Docker first; hosting later) and include catalog editing from the cloud in the first round. **2a done** — schema 26 outbox: triggers queue pointer rows (kind, record id) inside the business transactions; the uploader reads current JSON at send time (`Pos::outbox_batch` / `outbox_ack` / `requeue_all`), so rows stay small and mutable records coalesce to one pending row; the server must key by (kind, id). Rows accumulate (tens of bytes each) until a cloud is linked. **2b done** — `apps/pos-cloud` (axum 0.8 + PostgreSQL through tokio-postgres/deadpool; sqlx is not usable because its optional SQLite driver's `links = "sqlite3"` clashes with diesel's libsqlite3 in one workspace). Schema `migrations/001_init.sql` (accounts with Argon2id passwords, sessions and hubs storing token SHA-256 only, shops, 10-minute single-use 8-character link codes, `records` keyed (shop, kind, id) with JSONB data + `occurred_at`, `changes` queue). API `/api/v1`: accounts / sessions (bearer, 30 days), shops (list with hub status and pending edits, create, link-code, summary, products, changes), hub (link → hub id + token, revoking the shop's previous hub; upload ≤ 1000 records per batch in one transaction, answering acked seqs; changes; changes/ack with outcome). Owner edits are product patches (name, sku, category, price satang, on_sale, active), validated by shape on the server and authoritatively by the hub. Summary = sales/voids/refunds by Bangkok day, method, hour, top products, from the uploaded receipts with the pos-domain types. Local PostgreSQL: `apps/pos-cloud/compose.yaml` (port 5433). `tests/api.rs` drives the whole API with a real shop's outbox against a throwaway database (`POS_CLOUD_TEST_DATABASE_URL`; a Linux CI job provides PostgreSQL). Not yet: dashboard page (placeholder), 2FA, login rate limiting, TLS (expected from the hosting proxy). **2c done** — the main register syncs (`apps/pos-desktop/src/cloud.rs`, `cloud_ui.rs`): Settings → Devices & cloud links with the dashboard's code (`cloud.json`: server, hub ID, token, shop; device file, 0600, never in backups; only https:// except a local development server), then a `pos-cloud-sync` thread uploads the outbox in 500-record batches, acks, fetches owner edits and reports their outcome, every 30 s (60 s after a failure, "Sync now" wakes it). Database work runs as cloud jobs on the worker between commands (`Worker::cloud_submit`). Owner edits apply through `Pos::apply_cloud_change` (core `cloud.rs`): product patches only, run as the fixed Cloud member (`CLOUD_STAFF`, a `Session::cloud` that `authorize` accepts; reachable only from the worker, never a protocol request), attributed to Cloud in Activity; a new owner-chosen product ID adds the product (`save_product` now accepts an unknown given ID; archived stays refused); stock is never changed. Applied edits notify paired devices (`Topic::Catalog`) and the counter (`Event::DevicesChanged`). Linking requeues everything (a relink to another shop/server). Client-mode computers do not sync. Test `cloud_tests.rs` runs the real worker against a real server (skipped without `POS_CLOUD_TEST_DATABASE_URL`).

**Phase 2 (original plan).** An `outbox (seq, kind, id, json, created_at, sent_at)` written in the same transaction as receipts, voids/refunds, closed shifts, stock and ingredient movements, purchasing and Activity. An uploader thread sends batches with the hub's credentials; the server stores them idempotently by `(hub, seq)`. Downstream: versioned catalog/price/promotion/staff documents, applied on the hub through `pos-service` with HQ attribution (local edits stay possible; last applied version wins per record, shown in Activity). Encrypted daily database snapshot upload replaces "backup only on this machine". Owner web dashboard reads the uploaded records. Server: separate repository (Rust + PostgreSQL), accounts and 2FA for owners, PDPA notice before customer data (members, credit customers) is uploaded.

**Phase 3.** One hub per branch, each with its own sequences prefixed by a branch code (tax invoices per branch as Thai rules allow); HQ owns the catalog and prices (with optional branch price overrides); stock and drawers stay per branch; consolidated reports in the cloud.

## 6. Decisions still open

- **Tablet platform — decided: iPad first (2026-10-16).** Ordering tablets use a small web app served by the hub over the shop LAN and opened in Safari (added to the Home Screen), so no App Store app is needed. Safari only trusts the hub's TLS certificate after the iPad installs the hub's own root certificate: pairing shows a QR code that downloads a configuration profile (`.mobileconfig`) with that root, the staff installs it and enables full trust once (Settings → General → About → Certificate Trust Settings). The web app follows the design system (one theme, accent, Touch density) and only talks to the hub's protocol; it cannot take payment by default. A native iPad app stays an option if the web app falls short (e.g. printing from the tablet). Second registers and kitchen PCs use the desktop client mode.
- **Cloud hosting and budget** (phase 2): managed hosting in Thailand/Singapore region, cost per shop.
- **Real-shop trial:** Wi-Fi quality, wired hub, number of devices — phase 1 must be tried in a real shop before phase 2 starts. Windows runtime and real printers/drawers are still unverified (docs/validation.md).
