# Architecture

POS Heart is an offline desktop modular monolith. There is no HTTP server in the initial single-register scope.

## Modules

```text
apps/pos-desktop    egui screens, input state, worker messages, OS data paths
       ↓
crates/pos-core     catalog, checkout, held carts, history, persistence
       ↓
crates/pos-domain   Money, Product, Cart, Sale and validation
```

Three crates are deliberate: keep the business rules reusable and the UI independent without introducing speculative repository traits, network services, or one-method layers. Split pos-core only when a second real persistence implementation or frontend makes the split useful.

## Money and checkout

Money stores nonnegative i64 satang, accepts at most two decimal places, and uses checked arithmetic. Prices come from the catalog inside the transaction, not a UI-provided total; discounts are recomputed from those prices there too (see Discounts). Aggregate quantities for repeated product lines before validating stock. Note variants remain distinct receipt lines.

A checkout transaction must atomically create immutable sale snapshots, deduct tracked stock, remove a held cart, advance the receipt sequence, and record the stable cart ID. Retrying an already paid cart returns the original sale; it never deducts stock again. Insufficient cash, insufficient stock, validation errors and storage errors must leave every record unchanged.

Paid sales cannot be edited or deleted. Full-sale voids and partial refunds use separate immutable audit records. Product changes never rewrite past receipts.

## Threading

A single worker owns the database. The UI sends typed requests over a bounded channel and receives results; writes and queries never run in a paint callback. The worker requests a repaint on completion. Limit catalog/history result sets and avoid scanning all sales on every frame.

## Persistence decision

Confirmed SQLite via Diesel ORM with bundled libsqlite3-sys. Ordinary catalog, checkout, held-cart, history and void operations use the typed Diesel schema in schema.rs. Bound raw SQL handles SQLite PRAGMAs, versioned migrations, the UNION ALL daily activity report and VACUUM INTO backup. Both paths share one worker-owned connection; no extra service or async runtime. Pure Rust applies to application/UI; the user explicitly permits suitable dependencies. No database server installation. WAL + synchronous FULL; 8 MiB SQLite page cache; foreign keys; STRICT tables; checked schema user_version migrations in a transaction. Future versions are refused.

Database files live in OS-specific application data, never the source checkout. --data-dir overrides this; --demo uses a separate demo subdirectory. Backups use SQLite VACUUM INTO with a bound destination parameter to produce a consistent standalone snapshot, including committed WAL pages. Restore UI is not yet implemented; stop the app and preserve existing DB/WAL/SHM before an operator restores a verified backup. Never overwrite a live database.

## Initial scope and future seams

Retail and counter-service food share a cart, payment and sale model. Each product can opt into integer-unit stock tracking. Item notes and option groups (schema 006) support food instructions and priced modifiers. Held carts support returning to an order; tables and kitchen tickets (schema 15, see Tables and kitchen) build on them. Ingredient recipes, online ordering and multi-register sync remain outside scope; see [multi-device.md](multi-device.md) for the postponed multi-device proposal.

Future online ordering needs an explicit backend, authentication and synchronization design. Local transactions alone do not solve stock conflicts across disconnected registers.

## Full-sale voids

Migration 002 adds sale_voids keyed uniquely by the original cart ID. Checkout snapshots stock_tracked per line. An IMMEDIATE transaction reads the immutable receipt, aggregates original tracked quantities (including note variants), returns stock even for archived products, and inserts the refund audit record. Refund equals sale.total, not cash tendered. Retry returns the existing record; original receipts and sequences never change. Stock overflow, changed tracking, or audit-write failure rolls back everything.

Version-1 receipt JSON remains byte-for-byte unchanged. Its missing stock flags deserialize as None. A legacy void requires an explicit reviewed product-ID selection (empty is an explicit no-restock decision). Selections must refer only to legacy lines. If originally tracked units now point to an untracked product, the operator must restore stock tracking before retrying; the app never silently discards the return or turns tracking on.

## Daily reporting

A consistent read transaction combines sales in [Bangkok midnight, next midnight) with cancellation activity in the same interval. Money remains checked integer satang; report values use SignedMoney so prior-day refunds can produce negative net. Gross and counts reflect payment activity; refunds and void counts reflect cancellation activity, not the sale date. Net = gross - refunds. Product ranking subtracts returned units/receipt amounts on the refund day, groups by stable product ID, and limits to ten by net units, then net amount. Names and prices come from receipt snapshots. No DB work runs during paint.

## Shop preferences and startup

Desktop-only shop.rs owns a versioned local profile; it does not alter the sales schema or historical receipt identity. Save validates the trimmed name, writes/syncs a unique temporary file, and replaces shop.json. Load refuses corrupt/unknown formats and app state disables profile writes rather than replacing the evidence. Existing database detection precedes worker startup, so upgrading a store does not force onboarding. New empty stores require completion or an explicit skip; Demo bypasses onboarding.

Worker Data includes selected-date summary and a separate today_summary. When dates match it reuses the same report; otherwise it queries today separately. Home never labels selected historical activity as today. The Home refresh interval is a minute, not a continuous repaint loop. Shop profile drafts are UI state until Save and do not change sold receipt snapshots. Database snapshots intentionally exclude profile/theme/language files.

## Shift ledger and reconciliation

Migration 003 adds `shifts` and `cash_movements`, leaving every existing receipt/void byte unchanged and unassigned to a historical shift. A partial unique index enforces one open shift at the database level. Typed Diesel operations retain a JSON snapshot of each shift and immutable cash audit records. Paginated queries return at most 50 rows. Totals are updated inside each write transaction rather than scanning a growing ledger during paint or every refresh.

A new checkout/refund must find an open shift inside its IMMEDIATE transaction. Desktop requests carry the observed shift ID; stale IDs refuse rather than posting into a different shift. Sale audit amount is `total` (cash tender minus change), not tender. A refund posts to the active refunding shift, including refunds of old/unassigned receipts. Receipt, stock, held removal, sale/void audit, drawer movement and checked shift totals commit or roll back together. Paid-cart/void retry lookup precedes the active-shift gate, so retries after closing return the original result without another movement.

Opening and manual cash movement use stable UUID identities; retries with a different financial payload fail. Manual movements require a positive amount and a reason up to 240 characters. Zero opening/count is valid. Expected uses checked integer satang (a wide integer intermediate avoids false overflow during subtraction); negative balances remain explicit. Category totals and counters also check overflow.

Closing checks the shift revision observed in the confirmation, then records expected, counted and signed counted-minus-expected atomically. Concurrent payment either commits first and invalidates closing, or closing commits first and payment refuses; no payment can post after closing. Closed snapshots are not editable. A repeated close returns its original snapshot only for the same counted amount. Clock checks reject opening before the last close, events before opening and closing before the latest event. Event time order within an open shift can vary; last-activity tracks the maximum.

Worker Data contains active shift, a 50-row closed-shift page and a 50-row cash-record page. Home refreshes its separately labeled drawer status; Shifts also refreshes once per minute. Opening/closing does not reset calendar reports. Current unpaid carts block closing in the desktop UI; held carts remain unpaid and can resume in another shift. No physical drawer integration or multi-register sync is implied; optional staff sign-in is described under Staff and approvals.


## Payment methods (schema 004)

`PaymentMethod` and `PaymentRequest` live in domain; checkout accepts tender for Cash or the reviewed exact total for Transfer/Card. Noncash stores zero cash/change and revalidates the reviewed total against current catalog prices inside the same IMMEDIATE transaction. Mismatches roll back stock and held-cart changes. The desktop review pins cart, amount and observed shift ID; retry identity still returns the original receipt before new-method/gate validation. Single-method checkout is unchanged; a bill paid with several methods goes through split payment (below), which keeps the parts in the receipt JSON rather than adding payment rows.

Migration 004 rebuilds sales plus referencing sale_voids with foreign keys enabled, preserves receipt numbers/autoincrement high-water mark and all JSON verbatim, and retains cash-only versus noncash zero-tender SQL constraints. It adds constrained method columns and defaults legacy methods to cash. JSON defaults likewise read legacy snapshots without rewriting them. Migration remains in the opening IMMEDIATE transaction; unknown future schemas refuse startup.

Full void requires `refund_method == sale.payment_method` (a split sale refunds each part, see below); persisted audit and ledger carry that method. Refunding an older sale affects the current open shift. Original closed snapshots remain immutable. Existing Shift.sales/refunds retain their cash-only meaning; defaulted transfer/card sales/refund buckets are added. Counts include all methods. Every event advances the revision; expected drawer remains opening + cash sales − cash refunds + cash in − cash out. Manual cash movements reject noncash methods. DailySummary.payments accumulates checked method buckets by Bangkok event date; cash tender/change metrics include cash only.

The historical `cash_movements` table/API now also carries noncash sale/refund audit entries, explicitly labeled as payment records in UI. This naming remains for migration compatibility; never sum all its events as physical cash. Receipt, method, stock, held removal, refund, ledger and shift buckets commit together. No network processing or card credentials are involved.

## Split payment (no schema change)

Domain `payment.rs`: `Tender { method, amount }` and `SplitPayment { tenders, cash_given }`. `normalized()` merges parts per method in the order cash, transfer, card, drops zero parts, refuses fewer than two methods (`InvalidSplit`) and requires `cash_given` ≥ the cash part (zero when there is no cash part). `Pos::checkout_split(cart, &split, shift, now)` shares the checkout transaction: the bill is priced by `price_sale` without cash rounding and the parts must equal that exact total (`PaymentTotalChanged`), so the reviewed parts pin the amount. Cart-ID retry returns the original receipt before the gate.

The `sales` row keeps the first noncash part as `payment_method` with zero cash/change columns, which satisfies the migration 004 CHECK without a migration. The receipt JSON is authoritative: `Sale.tenders` (serde default empty, so single-method and legacy receipts are unchanged), `Sale.cash` = cash handed over and `change`; `Sale::paid_by()` returns the parts, or one part for single-method receipts. `shifts::record_all` writes one `cash_movements` row per part (the first keeps the sale ID, the others get new UUIDs) and counts the sale once; only the cash part changes drawer expected, transfer/card go to their buckets. Reports call `PaymentSummary::record_all(&sale.paid_by())`, so each part lands in its method bucket on the payment day; cash received/change come from `Sale.cash`/`change`.

A full void of a split sale refunds every part to its own method: `SaleVoid.tenders` (serde default empty; `refunded_by()` falls back to one part), one ledger row per part, and `sale_voids.refund_method` keeps the sale's primary method. A partial refund's `refund_method` must be one of the sale's paid methods (`InvalidRefundMethod`), and cumulative refunds by that method may not exceed what it paid (`RefundExceedsMethod`); the record and ledger entry use the chosen method. Single-method sales behave as before.

Desktop (`sale_ui.rs`): the payment segmented control's fourth option, Split, shows transfer and card amount fields; cash pays the rest, with a cash-handed-over field, change, quick-cash chips for the cash part and an equal-shares caption (2/3/4 people). "Review split payment" opens a confirmation listing each part, with a PromptPay QR for exactly the transfer part when an ID is set; confirming sends `Command::PaySplit`. History shows Split (coins icon) and "Split · cash + transfer" in details; receipts (`print/docs.rs`) print each part plus cash received/change; a split sale's refund dialog adds a Refund by control showing each method's remaining amount; the drawer opens when the sale has a cash part.


## Desktop UI layer (POS Design System v0.1)

`design/` is the design source of truth. `apps/pos-desktop/src/ui/` implements it for egui: `tokens.rs` is copied verbatim from `design/rust/tokens.rs` (only the `egui` import path differs and rustfmt skips it), `theme.rs` maps tokens onto egui styles for both themes and both densities and bundles the IBM Plex fonts, `widgets.rs` holds stateless primitives (buttons, fields, money/search inputs, segmented, tabs, chips, badges, kv rows, banners, dialogs, stat tiles, steps), `icons.rs` draws line icons, and `format.rs` owns money/date/time formatting. Screens read `Theme::of(ui)`; density lives in egui context data, so widgets need no extra arguments. `shell.rs` owns the top bar, workspace switcher, command palette and toasts. Display preferences (`theme.txt`, `density.txt`, `language.txt`) and `shop.json` stay outside the database and backups.

Sell, Products and History are laid out with explicit rectangles so the cart, category column, tables and inspectors keep stable sizes; the cart footer is an egui bottom panel, so totals and the pay button never scroll away. Reversible actions use undo toasts; irreversible or money-moving actions use blocking dialogs.

## Current bill autosave

The open bill is persisted through the existing held-cart store rather than a new table: a debounced background `hold` upserts it by cart ID, and `current-bill.txt` beside the database records which held cart is "current". On launch the worker resumes that cart in the background. An emptied or cleared bill sends a background remove. Checkout already deletes the held row in its IMMEDIATE transaction, so paying needs no extra cleanup; a late autosave of a paid cart is refused by `hold` (`AlreadyPaid`) and ignored. Background commands never change `busy` and never surface banners. Held-bill lists exclude the current cart ID. Closing the window waits (at most a few seconds) for a pending autosave before exiting.

## Catalog views and barcodes (schema 005)

Migration 005 adds nullable `barcode` (unique partial index) and `on_sale` (default 1) to `products`, plus a category index. `on_sale = 0` keeps the product listed and resumable in held bills but checkout refuses it with `NotForSale`; archiving (`active = 0`) still removes it from every list. `catalog(ProductQuery)` filters by search (name, SKU, category, exact barcode), exact category and saved view (low stock ≤ `LOW_STOCK`, out of stock, not for sale). `catalog_counts` returns totals per category and view in one read transaction. Bulk `set_on_sale` / `set_category` run in one IMMEDIATE transaction and refuse the whole batch if any product is missing or archived. `find_by_code` serves scanner input (exact SKU, case-insensitive, or barcode).

## Product options (schema 006)

`products.options_json` holds validated option groups (`json_valid`, array). Each group has stable IDs, a name, `required` and `multiple`, and 1–20 choices with a nonnegative price; at most 10 groups. Cart lines carry chosen `(group_id, choice_id)` pairs. Inside the checkout transaction `price_with_options` validates every choice against the current catalog (unknown, duplicate, too many in a single-choice group or missing required → `InvalidOptions`, whole checkout rolls back) and computes `unit_price = base + choices` with checked arithmetic. `SaleLine.unit_price` includes options and `SaleLine.options` snapshots group/choice names and prices (omitted when empty, so older receipts deserialize unchanged). Lines differ by options and note; stock aggregation per product is unchanged. Noncash review totals and the desktop cart use the same function, so a reviewed amount matches checkout exactly.

## Shift closing detail

`close_shift_with` takes a `ShiftCount`: counted total, reason and optional denomination breakdown. When the difference is nonzero the reason is required (`MissingDifferenceReason`); a non-empty breakdown must sum to the counted total (`CountMismatch`). Both are stored in the immutable closing snapshot with `#[serde(default)]`, so earlier snapshots read unchanged. `close_shift` (no reason) remains for existing callers. Shift numbers shown in the UI are positions in opening order (`shift_numbers`), computed in one scan rather than stored. Drawer-count drafts are desktop-local files (`drawer-count-<shift>.json`), removed after closing.

## Reports and exports

`DailySummary` also carries gross sales by Bangkok payment hour and units restocked by that day's refunds. The worker loads the same weekday one week earlier for comparison tiles and the hourly chart; percentage change uses integer arithmetic. CSV exports run on the worker thread, create a new file (never overwrite), prefix a UTF-8 BOM and neutralise formula-like text cells while keeping signed numbers numeric.

## Window sizing

`window.rs` keeps the window resizable with a 1000×700-point minimum. Each frame it converts the reported monitor size back to native points (egui reports it already multiplied by zoom) and, when the minimum would not fit after reserving room for a taskbar and title bar, sets the egui zoom factor to the largest 0.05 step that fits (floor 0.6), re-sends the minimum size and maximizes. It only manages zoom it set itself, so keyboard zoom by the user is respected. Full screen is a device preference in `window.txt`. Statement pages (Home, Shift, Reports, Settings) are laid out in a centred column of at most 1440 points.

## Stock movements (schema 007)

`stock_movements` records `initial`, `receive`, `remove` and `count` with before/after quantities and a reason. `adjust_stock` runs in one IMMEDIATE transaction: retry identity by request ID (same payload returns the original, different payload refuses), tracked products only, checked arithmetic, removals no larger than stock and with a reason, and counts refused with `StockChanged` when stock differs from the value shown when counting started. `save_product_at` records an `initial` movement when tracking starts and, with `keep_tracked_stock`, preserves the stored stock of a product that stays tracked, which closes a lost-update race between editing and selling. Sales and refunds are not duplicated into this table; receipts and refund records remain their history.

## Period reports

`summary(first, last)` generalizes the daily report to up to 366 Bangkok days in one read transaction, adding per-day gross/refunds and per-category net units/sales (current product category). `daily_summary(d)` is `summary(d, d)`. The desktop compares a single day with the same weekday a week earlier and a longer period with the equally long period before it.

## Partial refunds (schema 008)

`sale_refunds` holds immutable refund records (lines with index, units, option-inclusive amount and units restocked). `refund_items` looks up the request ID first, then requires an open shift, the original method (for split sales, one of the sale's methods within what it paid), an unvoided sale, a time after the sale and units within what is left after earlier refunds; legacy lines need an explicit restock review. Amounts use the receipt's unit price so they always match what was charged. Stock return, the record and the refunding shift's ledger entry commit together. `void_sale` refuses sales with partial refunds (`PartiallyRefunded`) and `refund_items` refuses voided sales (`SaleVoided`). Reports count partial refunds on their own day: refunds, method buckets, negative product/category units and amounts, restocked units, and `refund_count` separate from `void_count`.

## Discounts (no schema change)

`pos_domain::Discount` is `Amount(Money)` or `Percent(basis points 1..=10000)`. `off(price)` rounds percentages half up to the satang and refuses an amount above the price (`DiscountTooLarge`); invalid rules are `InvalidDiscount`. `CartLine.discount`, `Cart.discount` and `Cart.discount_reason` (optional, at most 240 characters, shared by the bill) are serde-defaulted, so held carts and older JSON load unchanged.

`price_bill(lines, bill)` prices discounts (it is now the discounts-only wrapper around `price_sale`, see Service charge, ++ prices and cash rounding): each line's gross (unit price with options × quantity) minus its own discount, then the bill discount on the remainder, spread over lines in proportion to their remaining amounts by largest remainder so the shares sum exactly. Checkout calls it inside the IMMEDIATE transaction from catalog prices and snapshots the result; the desktop cart (`App::bill_price`) and noncash review use the same function, and a reviewed amount must equal the discounted total. A free (zero) bill is valid; a discount over the price rolls back the whole checkout.

`SaleLine.total` stays gross (unit × quantity) and gains `discount_rule`, `discount` and `bill_discount`; `net()` is what was paid for the line. `Sale` gains `discount_rule`, `discount` (bill amount) and `discount_reason`, with `subtotal()` and `discounts()`; `Sale.total` is the amount paid. Legacy receipts deserialize with zero discounts (net = total) and are not rewritten. Partial refunds use `refund_share(line.net(), sold, already refunded, units)`, a cumulative floor so every partial refund of a line adds up exactly to its net (legacy receipts: unit price × units, as before); full voids still refund `sale.total`. Reports count gross sales as amounts paid, product/category sales from `net()`, and `DailySummary.discounts` as discounts given on the period's sales (a CSV row too).

## PromptPay transfer QR (desktop profile only)

`pos_domain::PromptPayId::parse` accepts a 10-digit mobile (leading 0), 13-digit national/tax ID or 15-digit e-wallet ID, ignoring spaces and dashes; `masked()` hides all but the last digits. `payload(amount)` builds the EMVCo Thai QR string (merchant tag 29 with AID A000000677010111; dynamic `010212` with amount tag 54, static `010211` without; CRC-16/CCITT-FALSE), matching the open-source promptpay-qr test vector. The ID is an optional `ShopSettings.promptpay` field in `shop.json` (still version 1, omitted when empty, validated on save and stored as digits). Older builds that deny unknown fields cannot read a profile containing it.

When set, the transfer review renders the QR (`ui/qr.rs`, `qrcodegen`, dark modules on white with a quiet zone in both themes) with the amount, shop name and masked ID. Payment is still `PaymentMethod::Transfer` with the same pinned review; nothing contacts a bank, and the cashier confirms receipt manually.

## Receipt printing (desktop only)

`apps/pos-desktop/src/print/` owns printing; core and domain are unaware of it. `PrinterSettings` lives in `printer.json` beside the database (version 1, `deny_unknown_fields`, written like `shop.json`); an unreadable or future file is refused, printing settings become read-only and the file is never overwritten. It is device-local and excluded from `VACUUM INTO` backups. `Connection` is None, Network (raw TCP, default port 9100, 4 s connect and 8 s write timeouts) or System (`lp -s -d QUEUE -o raw` through CUPS, queues listed with `lpstat -a`; Unix only, so Windows has network printing only). `Paper` is 58 mm (384 dots) or 80 mm (576 dots) at 203 dpi.

Documents (`docs.rs`: receipt with options, notes, unit price, line/bill discounts, refund notes, a copy mark on reprints and the footer; shift summary with drawer reconciliation, counted/difference, denominations and sales by method; test page) are built on the UI thread from committed data. `render.rs` rasterizes them with `ab_glyph` using the bundled IBM Plex Sans/Thai/Mono with Noto Sans Thai fallback and Thai-safe wrapping from `ui::text::break_lines`, so Thai prints as an image and needs no printer fonts. `escpos.rs` encodes ESC @, GS v 0 raster in 128-row bands, ESC d 4 feed, GS V 66 0 partial cut and, for cash payments with `open_drawer`, ESC p 0 25 250. Each job renders and sends on its own thread, one at a time; the outcome returns over a channel and requests a repaint.

Printing runs only after the worker has committed the sale or shift close and never feeds back into it: a failure shows a banner with Print again and dismiss, and the receipt, stock and ledger are unchanged. Auto-print and drawer pulse follow a successful payment; closing a shift with a printer configured prints its summary. No network use happens unless a network printer is configured (LAN).

## Print templates, preview and check bill (desktop only, no schema change)

`print/template.rs` defines `Templates { receipt: ReceiptTemplate, kitchen: KitchenTemplate }`, stored in `shop.json` as `templates` (serde defaults for every field, omitted while default so older profiles are unchanged; `validate` limits the title to 60 characters and header/footer to 8 lines and 400 characters). `ReceiptTemplate`: title (replaces the non-VAT "Receipt" heading; a small "not a tax invoice" line stays), header lines under the shop name, footer lines, logo on/off, `TextSize` Small/Normal/Large (scale 0.85/1/1.2), `DocLanguage` App/Thai/English, and switches for bill name, staff, unit price, options, notes, SKU, cash & change and `bill_qr`. `KitchenTemplate`: size (default Large), language, options/guests/staff; notes and cancellations always print. VAT receipts and tax invoices keep every legally required line whatever the switches say. A footer from the older printer settings is used until the template has its own.

Logo: `import_logo` accepts PNG/JPEG, fits it into 268×160 dots, flattens transparency to white, Floyd–Steinberg dithers to 1-bit and writes `receipt-logo.png` beside the database; `load_logo` reads it at startup. It is a business sidecar (`backup.rs` `business_file`) included in recovery folders, unlike `printer.json`.

`render.rs`: `Doc.size` scales all text; `Block::Image(Bitmap)` prints a centred 1-bit logo and `Block::Qr(payload)` a centred QR at about 45% of paper width with a quiet zone. `docs.rs`: `receipt(record, Brand { shop, logo }, template, lang, copy)`, `kitchen_ticket(ticket, kitchen template, lang)` and `check_bill(lines, BillPrice, cash total, label, brand, template, promptpay, lang)`: "Check bill · not a receipt", table/bill name, lines, items total, discount, service, VAT added, amount due (non-cash exact), an "if paid in cash (rounded)" note, a PromptPay QR for the exact amount when a PromptPay ID is set and `bill_qr` is on, and the footer. The check bill records nothing; `App::check_bill_doc` prices the cart with `pos_domain::price_sale` exactly like checkout.

`print_ui.rs`: `receipt_doc`, `check_bill_doc`, `preview_receipt`, `preview_check_bill`; `paper()` rasterizes any `Doc` with the print renderer into an egui texture cached by a hash of the document and paper width, shown on a white paper card, so the preview is exactly what prints. `preview_dialog` offers Print only when a printer is configured. Preview width follows the receipt printer's paper (else the unsaved draft's, default 80 mm). `templates_ui.rs` is the Settings → Printed documents card (Receipt / Check bill / Kitchen ticket tabs, controls left, live preview right, logo by path or file drop, Defaults / Discard / Save under the Settings permission).

## Staff and approvals (schema 009)

Domain `staff.rs`: `Permission` with per-role `Access` (the original fixed Owner/Manager/Cashier enum was replaced by data-defined roles in schema 012, see Custom roles). `StaffRef` is an immutable name/role snapshot; `Attribution { by, approved_by }` is stored on records. `discount_share_bp(discounts, subtotal)` rounds up so a limit is never exceeded by rounding. PINs are 4–8 digits.

Migration 009 adds `staff` (roster only: name, role, PBKDF2-SHA256 `pin_hash` with 60,000 iterations and a random salt, active, created_at), `app_settings` (`cashier_discount_limit_bp`, default 1000 = 10%) and nullable `stock_movements.staff_json`. Other records gain serde-default JSON snapshots — `Sale.staff`, `SaleVoid.staff`, `SaleRefund.staff`, `CashMovement.staff`, `StockMovement.staff`, `Shift.opened_by`, `ShiftClosing.closed_by` — so older JSON reads as unattributed and is never rewritten. Older builds refuse schema 9.

`Pos.session` holds the signed-in actor and a one-shot approver, in memory for the process only. `authorize(permission)` runs inside each write transaction after the retry-identity lookup and the shift gate: with no active staff it returns an empty attribution (unchanged behaviour); otherwise it requires a signed-in active member (`SignInRequired`) and then applies the actor's role access (see Custom roles). Guarded writes (as of schema 012) are listed under Custom roles; open and close shift snapshot the names. The first member must be an active Owner and is signed in; edits that would leave no active owner fail with `LastOwner`. Five wrong PINs in a row lock sign-in and approval for 30 seconds (`PinLocked`); inactive members cannot sign in or act. `DailySummary.staff` groups sales by who took payment and refunds by who processed them. The workspace builds sha2/pbkdf2/hmac at opt-level 3 in dev so hashing stays fast in debug builds.

Desktop `staff_ui.rs`: a lock screen whenever active staff exist and nobody is signed in (it blocks pages, dialogs, the palette and global keys); a top-bar name chip with Lock / switch user (`Ctrl L`); and an approval dialog opened when the worker refuses with `ApprovalRequired`. The app then replays the exact command as `Command::Approved { approver, pin, permission, inner }`; the worker verifies the PIN, sets the one-shot approver, runs the command and clears it, so an approval covers one command. A PIN identifies the person at the counter; it is not database encryption.

## VAT and tax invoices (schema 010)

Domain `tax.rs`: `TaxSettings { enabled, seller_name, tax_id, branch, address, rate_bp, pos_id }` (tax ID 13 digits with the Thai mod-11 check digit, `valid_tax_id`; branch "00000" for head office or 5 digits; rate 1..=3000 basis points, default 700; POS number optional). Settings are JSON in `app_settings` under key `tax`; `set_tax_settings` validates them and, when staff exist, needs the Settings permission (ManageStaff before schema 012). Prices are VAT-inclusive by default (`prices_include_vat`; ++ pricing is described below): `vat_included(amount, rate) = round_half_up(amount × rate / (10000 + rate))`.

When VAT is enabled, checkout snapshots `SaleTax` (seller details, rate, base, VAT) onto `Sale.tax` inside the same IMMEDIATE transaction; the receipt is the abbreviated tax invoice. `Sale.tax` is serde-default, so earlier receipts read as `None` and later settings changes never rewrite receipts.

Migration 010 adds `tax_invoices` (`number` INTEGER AUTOINCREMENT as the full-invoice running number, separate from receipt numbers; `sale_id` UNIQUE referencing the sale; `invoice_json`). `issue_tax_invoice(sale_id, buyer, now)` validates the `Buyer` (name, checked tax ID, branch, address), refuses receipts without a VAT snapshot (`NotTaxReceipt`) and voided or partly refunded sales (`SaleRefunded`: the invoice must come before refunds), and attributes the invoice to the signed-in staff. A retry with the same buyer returns the original invoice; a different buyer is `ConflictingRequest`. `SaleRecord.tax_invoice` carries it to history.

Migration 016 adds `credit_notes` (`number` AUTOINCREMENT as the CN running number, `sale_id`, `source_id` UNIQUE = the void or partial refund documented, `note_json`). `tax::credit_note(conn, sale, Credit, now)` runs inside `void_sale_for_shift` and `refund_items` after their ledger rows: when the sale has a full tax invoice it snapshots seller (`sale.tax`) and buyer (the invoice), the invoice number and date, the returned lines, `original_value` = the receipt's value before VAT, `difference` = refund − its VAT (a void's VAT is the sale's VAT; a partial refund's is Σ amount − `revenue_ex_vat`), `correct_value` = original − all earlier differences − this one (floored at zero), `vat` and `total`. Sales without a full invoice get none. A refund retry returns the stored refund before reaching this code, and `source_id` is unique, so notes never duplicate. `SaleRecord.credit_notes` (oldest first) carries them to history; recovery validates their JSON. Desktop: `print/docs.rs::credit_note` (title, original/copy, seller and buyer blocks, CN number, date, invoice reference and date, receipt, lines, the four values, total, reason, signature line) and `App::preview_credit_note`.

Reports: `DailySummary.vat_sales` sums sale VAT snapshots; `vat_refunds` counts a void's full sale VAT and a partial refund's `vat_included(refund, rate)`. CSV adds `vat_in_sales` / `vat_in_refunds`. Desktop `tax_ui.rs` holds the VAT settings card (Settings permission) and the buyer dialog; `print/docs.rs` renders the VAT receipt block and the full tax invoice (original/copy, seller and buyer blocks, lines at net amounts, value before VAT, VAT, total, receiver signature line). No VAT return or e-Tax filing is produced.

## Service charge, ++ prices and cash rounding (schema 011)

Domain `pricing.rs`: `PricingSettings { service_bp (0 = off, at most 3000), rounding: CashRounding { step 0/25/50/100 satang, mode Down (default, in the customer's favour) | Nearest (halves up) } }`, validated (`InvalidPricing`). `TaxSettings.prices_include_vat` (default true) selects VAT-inclusive or "++" prices. `PriceOptions::for_bill(pricing, tax, cart.service_charge, cash)` applies service only when the bill takes it, adds VAT on top only when VAT is enabled and prices exclude it, and rounds only cash payments. `percent_of` rounds half up.

`price_sale(lines, bill_discount, options)` (lines are gross, discount, service applies) prices in a fixed order: line discounts → bill discount (spread) → service charge on eligible lines (spread by eligible remaining amounts) → VAT on top (spread) → signed cash rounding (spread). `LinePrice` and `SaleLine` gain `service`, `vat_added` and `rounding` (i64), and `net()` includes them, so `refund_share` still returns exactly what was paid (a full refund of a rounded cash sale equals the paid total). `Sale` gains `service_charge`, `service_rate_bp`, `vat_added` and `rounding` (serde default/skip; legacy receipts unchanged). The receipt's `SaleTax` is computed from the amount actually paid, after rounding.

Migration 011 adds `products.service_charge` (default 1; off for e.g. retail goods in a restaurant) and `Product.service_charge`; `Cart.service_charge` (default true) is the per-bill toggle (takeaway). Pricing settings are JSON in `app_settings` key `pricing`; `set_pricing_settings` needs the Settings permission when staff exist. Checkout loads pricing and tax settings inside its transaction and calls `price_sale`; a noncash review must equal the unrounded total, and the drawer receives the rounded cash total. Reports add `DailySummary.service_charges` and signed `rounding`, with CSV rows `service_charges` and `cash_rounding`. Desktop: Settings → Pricing card, the VAT card's include/exclude switch, the product editor's service switch, Sell footer rows and the receipt rows (`history_ui::pricing_rows`) all use the same values.

## Custom roles (schema 012)

The fixed Owner/Manager/Cashier enum is replaced by shop-defined roles. `Permission` has ten values: Refund (partial), Void (whole sale), Discount (above the role's limit), CashMovement, CloseShift, Catalog, Stock, Reports, Settings (shop, pricing, VAT, printer, backups) and ManageStaff. `Access` is Allow, Approval or Deny. `RoleDef { id, name, access, can_approve, discount_limit_bp }`; a missing access entry (for example a permission added later) defaults to Approval, and custom roles can never grant ManageStaff (`InvalidRole`). `approves(p)` = (owner or `can_approve`) and the role allows `p`. Built-ins: `owner` is fixed in code (all Allow, approves, never stored or editable); `manager` allows all but ManageStaff (Deny) and approves; `cashier` has Approval for Refund/Void/Discount/CashMovement/Catalog/Stock, Allow for CloseShift/Reports, Deny for Settings/ManageStaff, does not approve, and keeps the previous shop-wide discount limit (default 10%).

`StaffRef.role` is now a role ID string (`owner`, `manager`, `cashier` or a UUID) with a `role_name` snapshot; older snapshots such as `"cashier"` still deserialize. `Staff.role` and `StaffInput.role` are strings. Migration 012 adds `roles (id, name, role_json)` and rebuilds `staff` without the old role CHECK. `ensure_roles` runs on open and creates manager and cashier once, carrying `app_settings.cashier_discount_limit_bp` into the cashier role; `set_discount_limit` / `discount_limit` are removed. API: `roles()`, `save_role` (ManageStaff; an empty id creates a UUID; the owner role is refused) and `delete_role` (built-ins refused; `RoleInUse` while any staff member, active or not, holds it; `RoleNotFound` for unknown IDs).

`authorize(p)` looks the actor's role up on every write, so edits apply immediately: Allow passes; Deny returns `Forbidden(p)` and no approval can override it; Approval needs an active approver who is a different person and whose role `approves(p)`, else `ApprovalRequired(p)`. `approve()` refuses self-approval. Guarded writes: checkout (any signed-in; a discount share above the actor's role limit needs Discount, and roles allowing Discount have no limit), `refund_items` (Refund), `void_sale` (Void), `move_cash` (CashMovement), open shift (any signed-in), close shift (CloseShift), product save/archive/bulk (Catalog), `adjust_stock` (Stock), VAT and pricing settings (Settings), `save_staff` / `save_role` / `delete_role` (ManageStaff). Reports and the shop/printer settings are checked in the UI or at file level; recovery backup/restore additionally checks Settings on the database worker (`staff_ui::access` / `may` / `discount_limit`). The approval dialog offers only members who may approve that permission, excluding the requester.

## Standard costs and estimated gross profit (schema 13)

`products.cost_satang` is an optional standard cost per sold unit, in integer satang: blank is unknown, explicit zero is known zero. Configure this cost inclusive of typical extras and exclusive of recoverable input VAT. Option-specific costs, purchasing, weighted-average inventory valuation and overhead are not modeled. Catalog edits never change prior cost snapshots. Checkout re-reads and snapshots `SaleLine.unit_cost` inside its write transaction; checked multiplication and the total standard cost must fit before committing stock/payment.

Receipt VAT is allocated exactly across paid lines by largest remainder and stored as `vat_share`. Profit reporting uses paid line amounts after discounts, service and cash rounding minus that VAT share. Partial refunds snapshot VAT-exclusive revenue using cumulative allocation against the line's refunded paid amount, so repeated refunds reverse the exact original revenue and standard cost; VAT-refund totals use those new snapshots too. Full voids reverse the original snapshot once. Event dates remain Bangkok payment/refund dates, and negative cost/profit on refund-only days is valid. Pre-13 receipts stay byte-identical and cost-unknown even after today's catalog cost is set; their VAT shares are derived only in memory.

`DailySummary.profit` separates covered revenue, net cost of goods, estimated gross profit, unknown-cost revenue and known/unknown units sold/refunded. Unknown costs never silently count as zero and do not enter the gross-profit estimate. This is not the shop's net profit, an accounting inventory ledger or a tax filing report.

## Recovery folders and activation

Desktop `backup.rs` owns version-1 `.posbackup` directories: `manifest.json` (time, schema/counts and fixed-name SHA-256 entries), a `VACUUM INTO` database, optional shop profile, current-bill marker, receipt logo (`receipt-logo.png`) and version-1 drawer drafts. Printer/display preferences, arbitrary paths, symlinks and unlisted files are excluded. Core `inspect_database` checks integrity, foreign keys, supported schema and counts without migrations. Confirm rehashes the reviewed source, copies and rehashes it into a sibling stage, migrates only that copy, validates every product and serialized business record in bounded pages, and checks settings/roster readers. A live backup flushes current-cart saves/deletions first. Settings authorization is checked against the database session before those operations.

Preparation creates a full safety bundle inside the current data directory. Printer/display files are copied from the live directory to the stage outside the portable bundle. A versioned sibling journal names the stage and previous directories with fixed prefixes; publication uses a synced temporary file and rename. The worker stops after preparation; the UI blocks further work and requests reopening. `main` calls `activate_pending` before reading settings or opening SQLite: rename live → previous, stage → live, remove journal. Previous data is never deleted. The safety bundle remains inside that previous directory and is restorable through the same UI. Unix directory syncs order publication/swaps. An interrupted swap resumes on next launch; an invalid stage refuses activation without replacing original data. Assumes one app instance per data directory. Windows directory durability and power-loss behavior remain unverified. The core retains standalone SQLite snapshot support; the recovery UI accepts versioned folders only.

## Product CSV import

Core `import.rs` parses bounded UTF-8 CSV (2 MiB / 5,000 records), including BOM, quoted commas/newlines and escaped quotes. Recognized headers: `sku,name,price,category,stock,barcode,on_sale,service_charge,cost`; first three required. Preview owns the exact reviewed source. Confirmation parses it again, authorizes Catalog and checks every code against current/archived products inside an IMMEDIATE transaction. New products, initial stock and activity commit together. There is no update/upsert or stock overwrite path. Worker file reads are bounded; the UI shows row issues and refuses confirmation until all rows are valid. Options are configured after import.

## Unified activity journal (schema 014)

`activity_events` is append-only through application APIs: sequence, timestamp, kind, entity ID and JSON business/actor/approver snapshots. Hooks run inside catalog, discount checkout, stock, refund, void and staff/role transactions. Audit failure rolls the whole write back; retry lookups precede hooks. Staff events omit PIN/hash fields. Historical data is not backfilled. Activity uses Reports access, literal search, type filters and 50-row newest-first pagination. Database work stays on the worker.

## Tables and kitchen (schema 015)

Domain `dining.rs`: `DiningTable { id, zone, name, seats, active }` (`validate` → `InvalidTable`). `Cart` gains `table: Option<Uuid>`, `guests` and `sent: Vec<SentItem>` (serde default/skip, so older held carts load unchanged); `Product`/`ProductInput` gain `kitchen: bool` (default true). `kitchen_changes(cart, kitchen_flag)` aggregates kitchen products by (product, options, note) and diffs them against `cart.sent`: positive quantities fire, negative ones cancel. `KitchenTicket { id, number, cart_id, table (name snapshot, or the bill name), guests, created_at, lines: Vec<TicketLine>, bumped_at, staff }`; a `TicketLine` with negative quantity is a cancellation and carries a `done` flag.

Migration 015 adds `dining_tables`, `kitchen_tickets` (`number` INTEGER AUTOINCREMENT, `bumped_at`, `ticket_json`) and `products.kitchen` (default 1). A table's open order is simply a held bill whose cart names the table; there is no separate order table. Recovery validation also reads kitchen ticket JSON and tables.

Core `dining.rs`: `dining_tables()`; `save_table` (Settings permission; switching off a table with an open bill → `TableBusy`; a duplicate active name in the same zone → `DuplicateTable`). `hold()` checks that the table exists and is active and holds no other bill (`TableNotFound` / `TableBusy`), so each table has at most one open bill and moving a bill is holding it on another table. `hold()` never changes the stored `sent`, so an autosave queued before a send cannot roll the kitchen state back.

`send_to_kitchen(cart, now)` is one IMMEDIATE transaction: it refuses paid bills (`AlreadyPaid`), checks the table, attributes staff, diffs against the **stored** `sent` (a lost reply or stale UI copy never re-fires dishes), holds the bill with the new state (an emptied bill is deleted, producing a cancellation), inserts a ticket with names/options from the catalog (archived products included) and records an Activity event of kind `kitchen` when dishes the kitchen already had are cancelled. `kitchen_tickets()` returns open tickets oldest first plus the 8 most recently bumped; `bump_ticket(id, Some(t) | None)` bumps or recalls; `set_ticket_line(id, index, done)` ticks a line (`TicketNotFound`). Paying deletes the held row, which frees the table; tickets stay until bumped.

`split_bill(cart, &[(line, units)], new_id, now)` splits a bill for separate payment in one IMMEDIATE transaction. It reads the **stored** `sent` state and calls `pos_domain::split_cart`, which moves the chosen units together with their kitchen-sent units (sent first), so neither bill fires or cancels anything. A percentage bill discount stays on both bills; a baht discount stays on the original only. The new bill has no table and no guests. At least one unit must move and one must stay (`InvalidBillSplit`). Both bills are held; a retry with the same `new_id` returns the stored pair. Desktop: More → Split the bill (bills with at least two units) opens a −/+ per line dialog; on success (`Event::Split`) the new bill opens for payment and the rest stays held or on its table, with a toast saying where.

Desktop: `tables_ui.rs::floor` draws the floor by zone with free/busy cards, the bill total priced like checkout, guests, minutes since the first ticket and unsent counts. The floor is a pane of Sell: with active tables, Sell's right side has Products / Tables tabs (Tables shows the busy count; `Alt 9`, `--page tables` and Ctrl K "Tables" open it, `Alt 9` again returns to Products; the workspace menu no longer lists Tables). Tapping a table loads its bill into the bill panel and switches to Products (a free table starts a new bill; an open counter or table bill is parked as held). The open table has a 3 px saffron border and "Open". The floor header has Counter / takeaway (new counter bill, parks a table bill) and a ghost Open kitchen screen · N. A table bill's header caption reads "Table · N guests" with a chevron; tapping it sets guests (−/+ and 1–6). More → Move to another table (or Seat this bill at a table for a counter bill) enters move mode: an info banner with Cancel, only free tables are tappable, the bill's label follows when it was the old table name, and it is autosaved at once. Sending a table bill to the kitchen parks it and shows the floor; paying or holding a table bill also returns to the floor. Sell's Held tab lists counter bills only (table bills live on the floor). Table bills have two footer modes: ordering (default) is one sunken total line (items · SC/VAT/discount detail · total in Money), Send to kitchen and a primary Take payment ฿total (F9); Take payment opens the full payment section (`SellState.paying` = that cart id) with a ghost Back to ordering (Esc) and a warning when dishes are unsent; the kitchen button is hidden there. Adding a dish or switching bills returns to ordering. Counter bills keep the inline payment section. Sell's "Send to kitchen (F10)" appears when tables exist. `kitchen_ui.rs` is a second OS window (egui immediate viewport) for a kitchen monitor; bump, recall and line ticks are background worker commands that never set `busy`. `PrinterSettings.kitchen` (`printer.json`, serde default, still version 1) selects Off, the receipt printer or a separate kitchen printer; print jobs queue so a kitchen ticket is never dropped while another job prints. `print/docs.rs::kitchen_ticket` renders large table name and dish lines, options, bold notes and `*** CANCEL ***` slips.

## Promotions (schema 17)

Migration 017 adds `promotions` (`id`, `promo_json`, `uses` ≥ 0, `updated_at`). `pos_domain::Promotion` holds the rule (`PromoRule::Off { discount }` — percent of the line or baht per unit —, `BuyGet { buy, free }`, `Bill { min_spend, discount }`), the target (`All`, `Product`, `Category`), `coupon` (stored trimmed and upper-case; unique, `DuplicateCoupon`), `max_uses`, `days` (bit 0 = Monday), `from_minute`/`to_minute` (equal = all day; may wrap midnight), inclusive `starts`/`ends` dates and `active`; `uses` comes from the column. `LocalTime::bangkok(unix)` gives the Bangkok date, weekday and minute without a time-zone library. `apply_promotions(lines, manual_bill, promos, when, coupons)` returns effective line discounts (a manual discount, or the best promotion as `Discount::Amount`), the bill discount (manual, or the best live spend-over promotion judged after line discounts) and which promotion gave each.

Checkout loads the promotions inside its IMMEDIATE transaction, applies them at the payment time, prices through `price_sale` as before, snapshots `SaleLine.promotion` and `Sale.promotions` (`PromoUse` id, name, amount), increments `uses` once per promotion per bill, and checks only the cashier's own discounts (total minus promotion amounts) against the discount limit and for the Discount activity event. The desktop's `App::promoted` runs the same function with `app.data.promotions` and the current time for the cart, line captions ("Promo name −x" in success colour) and the discount row. `promo_ui.rs` holds the Settings section (list with summaries and use counts; add/edit dialog with delete confirmation) and the coupon dialog (More → Enter coupon; codes must match a coupon promotion; at most five per bill). Receipts and history label promotion discounts by name; `history_ui::bill_promo` finds the bill-level one. Recovery validates promotions.
